# Setup CLI — Implementation Plan

**Date:** 2026-07-31

Implements `docs/superpowers/specs/2026-07-31-setup-cli-design.md`.

## Context

A fresh clone of this repo currently has no path from `git clone` to a working stack. `local/` is entirely gitignored (`.gitignore:61`), so a new clone has no account-creation script at all; `.env.example` produces a configuration that cannot reach the database from the host; nothing installs the pre-commit hook; and the only setup instructions live in a README snippet that stops at `docker compose up`.

This is the first of three subsystems supporting extreme-load testing (a load generator and a monitoring layer follow as separate designs). It needs to deliver two things: a genuinely one-command bootstrap, and **bulk account provisioning** — simulating extreme load means many concurrent simulated clients, each with its own API key, accumulated in a file a future load generator can read programmatically.

The shape is a Makefile front door over a Typer CLI: real program logic (hashing, bulk insert, Alembic invocation) lives in runnable Python under `cli/`; single existing shell commands (`poetry install`, `docker compose`, `pre-commit install`, `ruff`, `pytest`) stay as Makefile one-liners. Rationale for every decision is in the spec; this plan covers execution and the three things the codebase revealed that the spec doesn't yet account for.

One change to the spec: migrations move **entirely** into the CLI. The API container's startup migration is removed, so `make setup` / `make migrate` is the single migration path rather than one of two competing ones.

## What the codebase changed about the spec

1. **`local/` does not exist in a fresh clone.** It's gitignored wholesale, so it is never created by `git clone`. `open("local/accounts.csv", ...)` raises `FileNotFoundError` on the very first `make setup` — the exact scenario Phase 3 is meant to prove. `_create_accounts` must call `out.parent.mkdir(parents=True, exist_ok=True)` before writing.

2. **`.env.example` is missing `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`.** `docker-compose.yml:86-87` and the `createbuckets` entrypoint (`:107`) both interpolate them. The local `.env` has them (`.env:15-16`); `.env.example` does not. On a fresh clone the substitution yields empty strings, `mc alias set local http://minio:9000` receives two arguments instead of four and fails, and the S3 bucket is never created — while MinIO's own healthcheck still passes, so `--wait` returns clean and `make setup` reports success against a stack that cannot accept a single upload. Phase 0 fixes this alongside `POSTGRES_HOST`, and flips `APP_ENV` to `dev` for consistency with local use.

3. **The API container currently runs migrations on startup, and that gets removed.** `api/app.py:26-31` calls `command.upgrade(Config("alembic.ini"), "head")` inside `lifespan`, wrapped in `run_in_executor` — that file's answer to the same nested-event-loop constraint the spec describes in Design Decision 4, which independently confirms the spec's diagnosis. Left in place it would also race the CLI: `api` has no healthcheck in the compose file, so `docker compose up -d --wait` returns as soon as it is *running*, possibly mid-`lifespan`, and the host-side `upgrade` could overlap the container's.

   Migrations become the CLI's job exclusively — `make setup` and `make migrate`, nothing else. One migration path, one place to look when schema is wrong, and no race to reason about. This is Phase 2b below.

Also confirmed: the local `.env:3` is already `POSTGRES_HOST=localhost`, so Phase 0's second half is a no-op on this machine — only the tracked `.env.example` actually changes.

## Phase 0 — `.env.example`

Edit `.env.example` only (local `.env` already correct):

- `POSTGRES_HOST=postgres` → `localhost` (Design Decision 8 — `.env` describes the host; compose overrides with in-network names at `docker-compose.yml:9` and `:30`)
- `APP_ENV=prod` → `dev`
- Add `MINIO_ROOT_USER=minioadmin` / `MINIO_ROOT_PASSWORD=minioadmin`, matching the existing `S3_ACCESS_KEY`/`S3_SECRET_KEY` values

**Verify:** `python local/create_account.py` with no `POSTGRES_HOST=` prefix connects. Then `docker compose down -v`, copy `.env.example` to a scratch path and diff it against `.env` to confirm nothing else is missing, and bring the stack up — `docker compose logs createbuckets` should show the bucket created, and `api`/`worker` logs should show no connection errors (proving the `environment:` override still beats the changed `env_file`).

## Phase 1 — CLI foundation + account creation

**`pyproject.toml`** — add `typer` and `pre-commit` to `[tool.poetry.group.dev.dependencies]`, not the main group. The API and worker images install with `--only main,api` / `--only main,worker` (`docker/api.Dockerfile:13`, `docker/worker.Dockerfile:13`), so the dev group keeps both images unchanged while `poetry install` (which installs non-optional groups by default) still gets them onto the host.

**`cli/__init__.py`, `cli/commands/__init__.py`** — empty, matching the convention every package in this repo follows.

**`cli/main.py`** — exactly as the spec's Design Decision 2 sketch.

**`cli/commands/account.py`**

- `async def _create_accounts(count: int, out: Path) -> None` — the single implementation, ported and generalized from `local/create_account.py`. Reuse the existing pieces rather than reinventing: `get_settings()` from `shared/core/config.py`, `settings.sqlalchemy_engine_props` (`shared/core/settings/base.py:60-63`), `async_sessionmaker(engine, expire_on_commit=False)`, and the `Account` model (`shared/infrastructure/models.py:17-20`). Key generation must stay byte-identical to the auth path: `secrets.token_urlsafe(32)` hashed with `hashlib.sha256(key.encode()).hexdigest()`, matching `api/services/account.py:18` — anything else silently produces keys that never authenticate.
  - **Flush before writing the CSV.** `Account.id` is `autoincrement=True`, assigned by Postgres, so `account.id` is `None` until the INSERT reaches the server. `await session.flush()` (or commit) populates the IDs; `expire_on_commit=False` keeps them readable afterward without a reload, exactly as the existing script does.
  - **`out.parent.mkdir(parents=True, exist_ok=True)` before opening the file** — see finding 1.
  - Append semantics (Design Decision 3): if `out` doesn't exist, write the `account_id,api_key` header then the rows; if it does, open `"a"` and write data rows only. Print a one-line summary — never the keys.
- `def create(count: int = 1, out: Path = Path("local/accounts.csv"))` — the Typer command. Plain `def` wrapping `asyncio.run(_create_accounts(count, out))` (Design Decision 4 — Typer will not await a coroutine). Enforce positivity declaratively with `typer.Option(1, min=1)` so a bad `--count` is a usage error before any DB connection opens.

Delete `local/create_account.py` once `account create` is confirmed working.

**Verify:** `poetry run python -m cli.main account create`, then `--count 5`. Confirm six rows in `accounts`, that the CSV's `account_id` values match the real primary keys (a missing flush writes empty/`None` here), and that the file has one header and six data rows across the two runs. Confirm `--count 0` is rejected without touching the DB.

## Phase 2 — Environment bootstrap

**`cli/commands/bootstrap.py`**

- `def migrate()` — `alembic.command.upgrade(Config("alembic.ini"), "head")`, matching the invocation already in `api/app.py:30`. Note this is cwd-relative, as is `prepend_sys_path = .` in `alembic.ini:21`; `make` runs from the repo root, so this holds. Exposed as its own Typer command for standalone use after pulling new migrations.
- `def setup()` — plain `def`. Calls `migrate()` first, and **only after it returns** calls `asyncio.run(account._create_accounts(count=1, out=Path("local/accounts.csv")))`.

The sync/async structure is the load-bearing part. `command.upgrade()` executes `shared/migrations/env.py`, whose last line is `asyncio.run(run_migrations_online())` (`:34`) — so it is a synchronous call that opens and closes its own event loop internally. Making `setup()` or `migrate()` `async def` means a loop is already running when that line executes, and Python raises `RuntimeError: asyncio.run() cannot be called from a running event loop`. Two sequential, non-overlapping loops; both functions stay synchronous.

Wire both into `cli/main.py`.

**Verify:** against a freshly wiped DB (`docker compose down -v && docker compose up -d --wait`), run `poetry run python -m cli.main setup`. Migrations apply, one account is appended. Specifically confirm no `RuntimeError` about a running event loop — that error means the structure above was not followed.

## Phase 2b — remove the API startup migration

Only after `cli.main migrate` is confirmed working, so a replacement exists before the old path is removed.

In `api/app.py`: delete the `lifespan` function (`:26-32`) and change `:35` to `app = FastAPI()`. That strips the last use of five imports — `asyncio` (`:1`), `AsyncIterator` (`:3`), `asynccontextmanager` (`:4`), `command` and `Config` (`:7-8`) — all of which must go too or ruff's `F` rules will fail `make lint`. Verify `asyncio` has no other use in the file first; at present it does not.

Three consequences to be aware of, none blocking:

- **Plain `docker compose up` no longer produces a working API.** Previously the API self-healed a fresh volume; now a stack brought up without `make setup` has no tables and every request 500s. This is the main reason the README change in Phase 3 matters — `make setup` becomes the only correct entry point, not merely the convenient one.
- **After `make nuke`, the worker idles against an unmigrated DB** until `make setup` runs. It consumes from RabbitMQ and only touches the DB per message, so with an empty queue this is quiet and self-resolving, but expect DB errors in worker logs if anything is enqueued in that window.
- **Deployed environments lose their migration path entirely.** Nothing in `infrastructure/` applies migrations — the CDK stacks never reference Alembic, so the API's `lifespan` was the whole mechanism on ECS Fargate. Local development is fully covered by `make setup`; production is not, and needs its own answer (a one-off ECS task or a CDK custom resource running `alembic upgrade head` as a deploy step is the usual shape). **Out of scope here — track as future work.** Integration tests are unaffected: they build schema with `Base.metadata.create_all` (`tests/integration/conftest.py:37`), not Alembic.

Optional, low value: `docker/api.Dockerfile:15` `COPY alembic.ini ./` is now unnecessary in the image. Harmless to leave.

**Verify:** `docker compose down -v && docker compose up -d --wait`, then confirm the API is up but a request returns a DB error (no tables) — proving the startup migration is genuinely gone. Then `make migrate` (or `poetry run python -m cli.main migrate`) and confirm the same request succeeds. Run `ruff check .` to catch any import left behind.

## Phase 3 — Makefile front door + README

**`Makefile`** — as written in the spec's Components section: `.PHONY`, `COUNT ?= 1`, and the `setup` / `seed` / `migrate` / `nuke` / `test` / `lint` / `format` / `help` targets, with `help` self-documenting via the `target: ## description` grep convention. `setup` runs `poetry install` → `cp -n .env.example .env` → `docker compose up -d --wait` → `poetry run python -m cli.main setup` → `poetry run pre-commit install`. `nuke` is pure shell: `rm -f local/accounts.csv`, `docker compose down -v`, `docker compose up -d --wait`.

Two details worth not losing: `-n` on the `cp` means re-running `setup` never clobbers real local secrets, and `--wait` on both `up` calls blocks on the healthchecks that `docker-compose.yml:57-60` already defines — without it, the `make nuke && make setup` reset cycle races Postgres startup every time. A recipe line exiting non-zero aborts the target, which is the wanted behavior: an unhealthy stack stops setup rather than migrating against a database that isn't up.

**`README.md:114-121`** — replace the Local Dev snippet with `make setup`, state prerequisites as Poetry, Docker, and `make`, and point at `make help`. Leave the service address table. `README.md:129` — "Alembic migrations run automatically on API startup" — is false after Phase 2b and must be rewritten to say migrations are applied by `make setup` / `make migrate`. Leaving it would send a reader straight into the failure mode Phase 2b introduces.

**Verify — the real test is a genuinely cold start.** Clone into a fresh directory (no `.env`, no `.venv`, no `local/`), run `make setup` alone, and confirm it ends with: a healthy stack, a migrated DB, exactly one row in `local/accounts.csv`, a created MinIO bucket (`docker compose logs createbuckets`), and a working `.git/hooks/pre-commit`. Then:

- `make setup` again — safe to re-run, `.env` not clobbered
- `make nuke && make setup` — completes with no connection race
- bare `make seed` creates one account; `make seed COUNT=50` appends fifty
- an end-to-end smoke through Postman using a key from `accounts.csv`: `POST /documents` → presigned `PUT` → `POST /documents/{id}/process` → `GET /jobs/{id}` reaches `COMPLETED`. This is what actually proves the MinIO fix landed; the bucket's absence is invisible until an upload happens.
- `make test`, `make lint`, `make format`, `make help` each run without error

## Not doing

Per the spec's non-goals: no document/job commands (Postman covers those), no `nuke` Python layer, no DB-only reset, no MinIO bucket creation, no console-script entry point, and no changes to `local/create_document.py` / `upload_file.py` / `process_document.py`. No inline tests — testing is deferred to the end of the project; each phase gets the manual smoke check above instead.

**Follow-up this creates:** a production migration path. Phase 2b removes the only mechanism that applied migrations on ECS, and this plan deliberately replaces it for local development only. Deployed environments need a separate deploy-time step before the next infrastructure change ships.
